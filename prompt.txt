## Project goal

Build a CLI-based degree auditor prototype for:

* NUS B.Eng. Electrical Engineering
* AY2024 JC / non-poly intake
* EE Major requirements
* EE Technical Courses (TC)
* EE Technical Electives (TE)
* EE Specialisations
* SEP-mapped courses
* Excluding second major and minor requirements for now

The implementation should be source-aware and rule-driven. It should load curriculum rules from YAML configuration files, evaluate a student's completed/planned courses, produce a human-readable audit report, and generate machine-readable audit output.

This is a prototype, not an official graduation checker. Every implemented rule must carry a source reference and a human-readable description derived from the provided PDF documents.

## Non-goals for this prototype

Do not implement a web app.
Do not implement a full optimiser or CP-SAT solver yet.
Do not implement second major or minor audits yet.
Do not scrape live NUS pages yet.
Do not rely on an LLM at runtime.
Do not hard-code all rules inside Python code.
Do not make the system silently assume ambiguous curriculum rules. If a rule is ambiguous, model it explicitly and mark it as requiring human review.

## High-level design

Implement a Python CLI package called `degree_auditor`.

The system should separate:

1. Course data
2. Rule configuration
3. Course eligibility
4. Course allocation
5. Constraint evaluation
6. Audit reporting
7. Test cases

A key design principle:

Course eligibility is not the same as course allocation.

Example:
`EE3331C` may be eligible for TC, TE, Industry 4.0 core, and SPT elective. But in a specific audit scenario it may be allocated only to TC and Industry 4.0 core. The auditor must validate whether this allocation is allowed.

## Implementation requirements

Use Python 3.11+.

Recommended libraries:

* `pydantic` for config and data validation
* `typer` or `click` for CLI
* `pyyaml` or `ruamel.yaml` for YAML loading
* `rich` for terminal report rendering
* `pytest` for tests

Keep the implementation small and readable. Prefer deterministic, testable code over clever abstractions.

## YAML configuration design

The system must support hierarchical YAML config loading from a folder.

It should support commands like:

```bash
degree-auditor audit \
  --config configs/nus_ee_ay24_jc \
  --transcript examples/transcripts/simple_completed.yaml
```

It should also support loading multiple config folders/files and merging them by union:

```bash
degree-auditor audit \
  --config configs/nus_ee_ay24_jc \
  --config configs/nus_ee_ay24_jc/specialisations/robotics.yaml \
  --transcript examples/transcripts/robotics_with_capstone.yaml
```

Merge semantics:

* Lists of requirements are merged by `id`.
* Lists of course pools are merged by `id`.
* Lists of constraints are merged by `id`.
* Lists of specialisations are merged by `id`.
* If two objects with the same `id` are identical, accept.
* If two objects with the same `id` conflict, fail fast with a clear error unless an explicit `override: true` is set.
* Course pool includes should be unioned unless a conflict is detected.
* Excludes should also be unioned.
* Every loaded config object must retain `source_ref`.

Each rule and constraint must contain:

```yaml
id: string
description: string
source_ref:
  document: string
  page: int | null
  section: string | null
  quote: string | null
  notes: string | null
```

The `description` field should be human-readable and derived from the PDF rule text.

## Core rules to implement

### CDE Common Curriculum (60 units)

Model the Common Curriculum as individual pillars, not just two unit buckets.

General Education (24 units, six pillars, 4 units each). GESSxxxx/GECxxxx/GENxxxx are course
families -- match by prefix, not exact code:

* Singapore Studies: GESSxxxx
* Cultures & Connections: GECxxxx
* Communities & Engagement: GENxxxx (advisory: complete by Year 3)
* Critique & Expression: ES2631
* Digital Literacy: CS1010E
* Data Literacy: GEA1000 (former GER1000; treat as alias)

Interdisciplinary Skills / Core Skills & Knowledge (36 units, seven pillars + Integrated Project):

* Design Thinking: DTK1234
* Maker Space: EG1311 / EG1311BE
* Systems Thinking: IE2141 (or a TC in lieu -- see below)
* Artificial Intelligence: EE2211
* Sustainable Futures: CDE2501 (or a TC in lieu -- conditional)
* Creating Narratives: CDE2000 (or a TC in lieu)
* Project Management: PF1101
* Integrated Project: EE4002D/EE4002R (8 units) or CDE4301 (12 units, IDP)

Inflight TC substitution (AY2024 cohort). The 3 additional Technical Courses (TC, not TE) are
absorbed by vacated CC pillars or by UE; they do NOT add units beyond 160. Decision matrix
(GRB p.12 Options 1-4 / FAQ scenarios 1-16):

* If IE2141 not taken: a TC may satisfy Systems Thinking in lieu of IE2141 (IE2141 XOR TC-in-ST).
* If CDE2000 not taken: a TC may satisfy Creating Narratives in lieu of CDE2000 (CDE2000 XOR TC-in-CN).
* CDE2501 is ALWAYS compulsory and occupies exactly one pillar:
  * No GESS course taken => CDE2501 satisfies the Singapore Studies (GE GESS) pillar, AND a TC satisfies Sustainable Futures in lieu.
  * GESS course taken => GESS satisfies Singapore Studies, CDE2501 satisfies Sustainable Futures, and the third TC is read using UE (SF pillar cannot host a TC).
  * CDE2501 must never be double-counted across SS and SF.
* TCs that cannot be absorbed by ST/CN/SF pillars are read using UE space.
* This substitution table does NOT apply to RC4 / UTCP / NUSC / RVRC / poly-graduate students; flag such cases for human review.

### EE Major Programme

Implement the EE AY24 JC/non-poly major programme based on the checklist.

Include:

* EE1111A
* EE2111A
* EE2012
* EE2022
* EE2023
* EE2027
* PC2020
* exactly one of EE2026 or EE2028 for the major digital/microcontroller choice
* 2 EE Technical Electives

Model `EE2026 or EE2028` as a choice group. The course not used for the major may be eligible for TC.

### TC rule

Implement the AY24 JC/non-poly Technical Course rule:

* Minimum 3 TC (= 12 units).
* TC is separate from TE.
* TC and TE must be mutually exclusive.
* The TC pool is a CLOSED list. Do not accept arbitrary EE3xxxC/EE3xxx as TC.
* SEP courses may be mapped to TC for AY23/AY24 intakes.
* Eligible TC courses (the entire closed set):

  * EE2026 or EE2028, whichever is not used to fulfil EE Major
  * EE3033 (Systems Integration and Design Lab), TC-eligible from Sem 2 AY2025/26 (Sem 1 & 2 from AY2026/27); not an extended core; not a TE
  * EE3131C
  * EE3408C
  * EE3331C
  * EE3431C
  * EE3731C (Signal Analytics)
  * EE3104C

### TE rule

Implement the EE Technical Elective rule:

* Minimum 2 TE.
* Eligible TE courses:

  * EE4xxx
  * EE3xxxC
  * EE3xxx
  * For AY2024 intake specifically: CG3207, EE3105, EE3305, EE3306, EE3703, EE3801 are valid TEs (the UE-only restriction on these applies to AY2025 intake and after).
* Exclusions:

  * EE3033 is not TE.
  * EE3031 can only fulfil UE for AY2021-AY2024 intake, not TE.
  * Non-EE courses (MExxxx, CSxxxxDE, RBxxxx) cannot fulfil the EE TE rule (UE only). This includes the non-EE twins of cross-listed courses, e.g. ME3243 (twin of EE3305), ME3163 (twin of EE3306), ME3142 (twin of EE3331C). The non-EE twin may still satisfy a Specialisation elective, but never the TE rule.
* TC and TE are mutually exclusive.
* SEP special rule:

  * At least one TE, either EE3xxxC or EE4xxx, must be done at NUS.
  * At most one SEP-mapped EE3xxxC/EE4xxx may be used to fulfil Major TE.

### UE treatment

Model UE as residual graduation capacity, not as a normal double-counting requirement.

Specialisation courses can occupy UE space without consuming the specialisation's 8-unit double-counting budget, unless they are also allocated to another explicit requirement such as TE, TC, Common Curriculum, or another Specialisation.

### Graduation-level constraints

Enforce these (resolved from earlier ambiguities):

* Level-1000 cap: no more than 60 units of level-1000 courses count toward the degree (excludes POY1901/2/3/8/9, POY1910T, CFG1010, ES1103, CFG1002, DYOC courses). Extra units beyond 60 do not count toward graduation but still count to GPA.
* Internship: the major internship requirement is 10 units, drawn from the internship course pool. Model it fully (per the CDE Engineering Internships page):
  * Course pool: EG3611A IA (10u), EG3612 VIA (6u), CFG2101 VIP (4u), CDE2605/CDE2605R UROP/UREx (4u each; EG2605 is the legacy code -> alias to CDE2605), ETP3201/3205/3206/3207 (NOC), EG3611P (10u, poly APC). CP3880/CP3200/CP3202 (ATAP/SIP) are CEG-only and NOT valid for the EE internship.
  * The 10 units may be a single course or a combination summing to >=10, e.g. EG3611A (10); EG3612 (6) + CFG2101 (4); EG3612 (6) + CDE2605 (4). A combination short of 10 (e.g. 4 + 4 = 8) does not satisfy it.
  * At most 4 units of UROP/UREx (CDE2605/CDE2605R) may count toward the major internship; excess UROP/UREx units go to UE.
  * Up to 20 units of unit-bearing internships may be taken; at most 10 count toward the major requirement and the remainder counts toward UE (no double-credit to the major).
  * Poly-direct-entry students receive APC for EG3611P (10u); they may still take up to 10 further internship units counted toward UE.
  * Advisory: Stage 3 standing; IA/VIA graded CS/CU.
* SEP residency: at least 50% of overall course units must be read at NUS; at least 60% of programme course requirements must be read at NUS.
* S/U option / grade-free scheme is OUT OF SCOPE for this prototype.

### Specialisation global policy

Every EE Specialisation should inherit:

```yaml
total_units: 20
max_overlap_units: 8
min_distinct_units: 12
```

A specialisation allocation overlaps if the same course units are also allocated to another explicit non-UE requirement.

If a course is allocated to a Specialisation and residual UE only, this does not count as overlap.

### Capstone special rule

Implement the capstone lock:

If EE4002D or EE4002R is double-counted between Common Curriculum and a Specialisation, then that entire 8-unit overlap budget is consumed, and no further technical elective may be double-counted for that same Specialisation.

This applies to:

* SPT, where satellite-related capstone is compulsory in the standard path
* Robotics, if robotics-related capstone is used
* IoT, if IoT-related capstone is used
* MQM, if MQM-related capstone is used

Also implement:

* If capstone is used to fulfil SPT, IoT, Rbt, or MQM, then no SEP courses may be mapped to that respective Specialisation.
* CDE4301/CDE4301A cannot fulfil a Specialisation in any Engineering major if it is also used to fulfil the IDP Second Major. (This is separate from the EE4002D/R 8-unit capstone overlap lock, which remains restricted to EE4002D/EE4002R.)

### SEP rules

Support SEP-mapped course attempts.

Each SEP attempt may have:

* original overseas course code
* mapped NUS equivalent
* approved target requirements
* units
* approval status

Implement these constraints:

* For Major TE:

  * At least one TE, either EE3xxxC or EE4xxx, must be completed at NUS.
  * At most one SEP-mapped EE3xxxC/EE4xxx may be used for Major TE.
* For Specialisations:

  * At most 8 units of unique SEP courses may be mapped per Specialisation.
  * A SEP course approved for one Specialisation should not be mapped again to another Specialisation or Minor.
  * Since minor is out of scope, still implement the data structure generally, but only test cross-specialisation conflict.
  * If capstone is used for SPT, IoT, Rbt, or MQM, no SEP courses may be mapped to that same Specialisation.

## Allocation strategy

Implement a simple allocation pipeline for now.

Stage 1: Eligibility expansion

For every course attempt, compute all eligible requirements and course pools.

Stage 2: Trivial greedy allocation

Use a deterministic, simple allocation priority:

1. Fixed EE Major core
2. EE2026/EE2028 major choice
3. Common Curriculum capstone if present
4. TC
5. TE
6. Selected Specialisations
7. residual UE

Keep the greedy allocator intentionally simple and explainable. Do not try to optimise globally yet.

Stage 3: Manual allocation override

After greedy allocation, allow exporting an intermediate editable YAML file:

```bash
degree-auditor plan-allocation \
  --config configs/nus_ee_ay24_jc \
  --transcript examples/transcripts/robotics_with_capstone.yaml \
  --out tmp/allocation.yaml
```

Then allow the user to edit `tmp/allocation.yaml` and run:

```bash
degree-auditor audit \
  --config configs/nus_ee_ay24_jc \
  --transcript examples/transcripts/robotics_with_capstone.yaml \
  --allocation tmp/allocation.yaml
```

Manual allocation should override greedy allocation, but constraints must still be evaluated. Invalid manual allocations should produce clear errors or failed constraint results.

## Test cases

Generate a complete structured test suite.

Each test case must have:

```yaml
id: string
description: human-readable description
transcript: ...
manual_allocation: optional
expected:
  pass: true | false
  satisfied_requirements: []
  failed_requirements: []
  failed_constraints: []
  warnings: []
```

An expanded, source-referenced set of edge cases (closed TC list, non-EE-not-TE, CG3207/EE3305 AY2024 TE carve-outs, SEP->TC mapping, CDE4301 vs IDP, SEP residency, Emerging-Tech exclusion, etc.) is maintained in `review/edge_cases.yaml`. Implement these test cases at minimum:

1. `major_core_pass_basic`

   * Student completed all fixed EE major core courses, one of EE2026/EE2028, and 2 valid TEs.
   * Expected: major passes.

2. `tc_te_mutual_exclusion_fail`

   * Same EE3xxxC course manually allocated to both TC and TE.
   * Expected: fail TC/TE mutual exclusion.

3. `ee2026_ee2028_choice_tc_success`

   * EE2028 used for Major, EE2026 used for TC.
   * Expected: valid.

4. `ee3031_not_te_fail`

   * EE3031 manually allocated as TE.
